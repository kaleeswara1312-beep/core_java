Spring Security Infrastructure Components

DelegatingFilterProxy

A standard Servlet Filter registered with Tomcat. It bridges the gap between the Servlet Container's lifecycle and Spring's ApplicationContext by looking up and delegating to a Spring Bean (typically named springSecurityFilterChain).

FilterChainProxy

The actual Spring Bean that receives requests from DelegatingFilterProxy. It contains a list of SecurityFilterChain beans and determines which chain matches the incoming request based on RequestMatcher rules.

SecurityFilterChain

An interface defining a list of security filters (e.g. JwtAuthenticationFilter, AuthorizationFilter) that should be applied to matching URL patterns. Configured via SecurityFilterChain bean definition in Spring Boot 3.

Multiple SecurityFilterChain Matching Logic

FilterChainProxy evaluates registered SecurityFilterChain instances sequentially based on order.

Order(1) - API Chain URL: /api/**

// Java Configuration

@Bean

@Order(1)

public SecurityFilterChain apiChain(HttpSecurity http) {

http.securityMatcher("/api/**")

.sessionManagement(s -> s.sessionCreationPolicy(STATELESS))

.addFilterBefore(jwtFilter, ...);

}

JwtAuthenticationFilter
AuthorizationFilter
Order(2) - Admin / Form Chain URL: /admin/**

// Java Configuration

@Bean

@Order(2)

public SecurityFilterChain adminChain(HttpSecurity http) {

http.securityMatcher("/admin/**")

.formLogin(Customizer.withDefaults());

}

UsernamePasswordAuthenticationFilter
DefaultLoginPageGeneratingFilter
AuthorizationFilter

Key Architectural Rule for Multiple Chains

When a request enters FilterChainProxy, it iterates through all registered SecurityFilterChain beans in ascending order of their @Order annotation. The first chain whose RequestMatcher returns true handles the request exclusively. Subsequent chains are completely ignored.

Top Spring Security Architectural Interview Q&A

Q1: How does Spring Security integrate with Servlet Container filters?

Servlet Containers (like Tomcat) do not know about Spring ApplicationContext or Spring Beans. Spring Security uses DelegatingFilterProxy (a standard Servlet filter registered in Tomcat) to bridge this gap. DelegatingFilterProxy delegates the incoming request to a Spring-managed Bean named springSecurityFilterChain (an instance of FilterChainProxy).

Q2: What is the difference between a Servlet Filter and a Spring MVC Interceptor?

Servlet Filters belong to the Servlet container and execute before DispatcherServlet. They cannot access Spring MVC handler method details. Interceptors belong to Spring MVC, execute inside DispatcherServlet after request mapping, and have access to the target Controller method (Object handler) and Spring View objects.

Q3: What happens if Authentication fails in a Spring Security filter?

If authentication fails (e.g. invalid JWT token), the filter throws an AuthenticationException. The AuthenticationEntryPoint handles this exception and directly writes an HTTP 401 response back to the client. The request chain is halted immediately, meaning DispatcherServlet, Interceptors, and Controllers are never reached.

Q4: Where is the authenticated user stored in a stateless REST API?

In a stateless REST API (JWT based), an Authentication object is constructed on every request by the JWT filter and stored in the SecurityContextHolder.getContext() (typically backed by ThreadLocal). At the end of the request execution, the SecurityContext is cleared so no HTTP session state persists across requests.
